# EFC — файловый канал. Стандарт efc/1, редакция 1.1 (черновик)

Протокол: `efc/1`.

EFC — способ, которым программа (сервер) и её клиент (агент, скрипт, другая программа) обмениваются вызовами
через общую папку, когда прямой связи между ними нет: клиент работает в виртуальной машине, контейнере, песочнице
или на другой ОС, а видит только примонтированную папку.

Ключевые слова: **обязан** — требование; **следует** — рекомендация, отступать можно с причиной; **может** — по
желанию.

## 1. Термины

- **Сервер** — программа, которая выполняет вызовы и ведёт канал.
- **Клиент** — тот, кто просит.
- **Канал** — папка, в которой они встречаются.
- **Вызов** — одна просьба (команда с аргументами) и её итог.
- **Подопечный** — то, чем управляет сервер (редактор, сборочная система, база…), если он не выполняет всё сам.

Сервер не обязан быть тем, кто делает работу: он может передавать вызовы подопечному. Клиенту это не видно.

## 2. Раскладка

```
<канал>/
  channel.json        паспорт канала                      ← сервер
  README.txt          то же для человека                  ← сервер
  alive.json          пульс                               ← сервер
  efc[.exe]           клиент (может)                      ← сервер
  requests/<id>.json  запросы                             ← клиент
  cancel/<id>.json    просьбы отменить                    ← клиент
  active/<id>.json    принятые вызовы: фаза, прогресс     ← сервер
  done/<id>.json      итоги                               ← сервер
  trash/              корзина                             ← клиент переносит, сервер чистит
  inbox/<key>.json    что ждёт действия клиента (может)   ← сервер
  state/*.json        снимки состояния (может)            ← сервер
  artifacts/          крупные результаты (может)          ← сервер
  trace/              журналы трассировки (может; не часть протокола)
  .gitignore          "*"                                 ← сервер
```

Клиент **обязан** писать только в `requests/` и `cancel/` и переносить файлы в `trash/`. Остальное пишет сервер.

Сервер **может** вести подканалы с той же раскладкой в подпапках (например, отдельный подканал для длинных
сценариев); каждый объявляется в `channel.json` → `subchannels`.

## 3. Файлы

### 3.1. Атомарная запись

Любой файл канала **обязан** появляться целиком: запись во временный файл в той же папке
(`<имя>.tmp` или `<имя>.tmp-<случайное>`), затем rename поверх. Сервер и клиент **обязаны** игнорировать файлы,
которые не оканчиваются на `.json`, и файлы, имя которых начинается с точки.

На Windows rename поверх файла, который в этот момент открыт другим процессом (антивирус, индексатор, читатель),
может не пройти — ошибкой доступа или блокировки (5, 32, 33). Сервер **обязан** повторить (до 10 раз через
20–50 мс), затем — на следующем такте, не теряя записи. То же относится к удалению: не убранный файл сервер
убирает позже.

Файл канала **никогда** не переписывается на месте — только новым файлом и rename. Общие папки ВМ кешируют
содержимое: файл, переписанный на месте, клиент может видеть старым (наблюдалось на практике). Исчезновение
файлов (удаление, перенос сервером) клиент в ВМ тоже может увидеть с задержкой в секунды: клиент **не должен**
делать выводы из того, что файл «ещё есть»; признаки событий — появление файлов (`active/<id>`, `done/<id>`) и
смена `seq`.

### 3.2. Клиент не удаляет

Клиент **может не иметь права удалять** файлы в общей папке (так устроены многие песочницы: создать, переименовать
и заменить rename'ом можно, удалить — нет). Поэтому:

- клиент **следует** пытаться удалить, а при отказе **обязан** перенести файл в `trash/` этого же канала
  (перенос между разными точками монтирования превращается в копирование и исходник не убирает);
- протокол **никогда не требует** от клиента удаления: всё, что клиент «убирает», он убирает переносом;
- удаляет только сервер (раздел 7).

### 3.3. Чтение

Файл может исчезнуть или ещё не появиться — это не ошибка, повторить позже. Если сервер не может разобрать JSON
запроса, а файлу меньше 2 с, он **обязан** отложить запрос; старше — итог с кодом 2.

### 3.4. Кодировка

Писать UTF-8 без BOM, переводы строк LF. Читать — с BOM и без.

### 3.5. Идентификаторы

`^[a-z0-9_-]{1,64}$` — только строчные (на части файловых систем регистр имён не различается); кроме имён
устройств Windows (`con`, `prn`, `aux`, `nul`, `com0`–`com9`, `lpt0`–`lpt9`). id задаёт клиент,
он совпадает с именем файла. Рекомендуемый вид — `ГГГГММДД-ччммсс-ммм-<6 hex>` (UTC): сортируется по времени и
уникален. id — ключ идемпотентности: id, который уже есть в `active/`, `done/`, в корзине как `done-<id>.json` или
был выполнен в пределах `keep`, повторно не выполняется — в том числе после перезапуска сервера.

### 3.6. Размеры

Запрос — не больше `limits.requestBytes` (по умолчанию 1 МБ). Текстовый вывод — не больше `limits.outputChars`
(по умолчанию 512 К символов), лишнее обрезается с `"truncated": true`. Больше — файлом (раздел 9).

### 3.7. Время и часы

Время — ISO 8601 UTC. Часы клиента и сервера могут расходиться (часы ВМ и хоста). Решения «пора / не пора»
каждая сторона **обязана** принимать по своим часам: сервер — по mtime и своему времени, клиент — по своему.
Живость сервера определяется по смене `seq` в `alive.json`, а не по полю `at`.

### 3.8. Опрос

Уведомления файловой системы (inotify, FSEvents, ReadDirectoryChangesW) на общих папках ВМ теряются. Они **могут**
ускорять работу, но сервер **обязан** опрашивать `requests/` и `cancel/` сам, не реже чем раз в 200 мс. Клиенту
**следует** опрашивать часто в первые секунды ожидания (20–50 мс) и реже потом (до 500 мс). Эталонная реализация
опрашивает раз в 20 мс: чтение маленькой папки почти ничего не стоит, а вызов укладывается в ~20 мс плюс задержку
самой общей папки.

## 4. channel.json — паспорт

```json
{
  "protocol": "efc/1",
  "instance": "build-server@host-01:/srv/app",
  "server": "build-server", "version": "1.4.0", "pid": 4120,
  "started": "2026-01-15T09:00:00Z",
  "title": "Сборка приложения",
  "howToStart": "Запустите сервер сборки: build-server --channel /srv/app/.efc",
  "roots": { "channel": ".", "project": ".." },
  "beat": 2,
  "limits": {
    "requestBytes": 1048576, "outputChars": 524288,
    "defaultTimeout": 600, "defaultKeep": 300, "minKeep": 60, "maxKeep": 86400,
    "trashMaxAge": 86400, "artifactKeep": 86400, "queue": 100
  },
  "features": ["cancel", "batch", "steps", "lock", "inbox", "state", "artifacts"],
  "commands": [
    { "name": "build", "summary": "Собрать проект", "usage": "build [--release]", "long": true },
    { "name": "test",  "summary": "Запустить тесты", "usage": "test [--filter <regex>]", "long": true, "idempotent": true },
    { "name": "trash.clean", "summary": "Очистить корзину канала", "usage": "trash.clean [--dry]", "readOnly": false }
  ],
  "reasons": ["build-failed", "tests-failed", "busy", "no-approval"],
  "subchannels": { "scenarios": "scenarios/" },
  "state": { "status": "state/status.json" }
}
```

- `instance` — кто владеет каналом. Сервер **обязан** обслуживать только канал со своим `instance`: если в папке
  чужой `channel.json` (папку скопировали или синхронизировали с другой машины), сервер не берёт запросы и пишет
  предупреждение в свой журнал. Проверка — при старте и периодически (не реже раза в минуту): подменённый на ходу
  паспорт переводит сервер в `state: "degraded"` с `detail.foreignInstance`, запросы не принимаются. Пропавший
  паспорт сервер записывает заново. Имя машины в `instance` берётся из ОС, а не из переменных оболочки, — иначе
  перезапуск из другой оболочки выглядит чужим.
- `howToStart` — что сделать человеку, чтобы сервер заработал. Клиент печатает это при кодах 10 и 13: сам клиент
  сервер обычно запустить не может.
- `roots` — пути относительно папки канала; по ним клиент переводит пути из ответов в свои.
- `commands` **может** быть неполным, если сервер поддерживает команду `help`.

## 5. Вызов

### 5.1. Запрос — `requests/<id>.json`

```json
{
  "v": 1,
  "id": "20260115-090301-120-a1b2c3",
  "command": "test",
  "args": ["--filter", "parser"],
  "params": {},
  "from": "agent",
  "created": "2026-01-15T09:03:01Z",
  "timeout": 600,
  "keep": 300,
  "force": false,
  "lock": false
}
```

- `command` обязателен. `args` — список в стиле командной строки, `params` — объект; команда берёт то, что ей нужно.
- `from` — подпись для журнала. Прав не даёт (раздел 12).
- `timeout` — предел от появления запроса до итога, с. `keep` — сколько хранить итог, если клиент его не забрал,
  с (не меньше `limits.minKeep`).
- Поле `token` и любые секреты сервер **обязан** отбрасывать и в канал не писать.

### 5.2. Пакет

```json
{ "v": 1, "id": "…", "onError": "stop",
  "batch": [
    { "command": "record.comment", "params": { "record": "r-17", "text": "Проверено" } },
    { "command": "record.status",  "params": { "record": "r-17", "to": "done" } } ] }
```

`onError`: `stop` (по умолчанию) или `continue`. Пакет не транзакционный, если сервер не объявил `atomicBatch` в
`features`: выполненные до ошибки элементы остаются выполненными. Итог по каждому — в `items[]`, по элементу на
каждую команду пакета в том же порядке (выполненные, пропущенные, отменённые). Сервер с пакетами объявляет `batch`.

#### 5.2.1. Шаги

Сервер, объявивший `steps`, понимает у элементов пакета:

| Поле | Что |
|---|---|
| `id` | имя шага: `^[A-Za-z0-9_-]{1,32}$`, уникальное в пакете; по умолчанию `s1`, `s2`, … |
| `expect` | проверка результата: `exit` (ожидаемый код, по умолчанию 0), `output` (подстрока есть в выводе), `notOutput` (подстроки нет), `data` (поля `data` по пути через точку и их значения) |
| `always` | выполнять и после остановки пакета — по ошибке, отмене или сроку (уборка) |
| `onError` | `stop` / `continue` для этого шага (иначе — как у пакета) |
| `timeout` | предел шага, с; вышел — шаг прерывается, код 5, `reason: "step-timeout"` |

**Подстановка.** В `args`, строках `params` и в `expect` ссылка `${шаг.путь}` заменяется значением из итога уже
выполненного шага: путь — в его `data` через точку (индексы массивов — числами: `${a.items.0.name}`); особые
имена — `exitCode`, `output`, `ok`. Строка ровно из одной ссылки в `params` и `expect.data` получает значение как
есть (число, объект); иначе — текст. Ссылка на шаг, который ещё не выполнен, или на поле, которого нет, — шаг не
выполняется, код 2, `reason: "bad-reference"`.

**Исход шага.** Шаг успешен, когда сходится `expect` (без него — код 0). Ожидаемая ошибка (`"expect": {"exit": 3}`)
— успех. Команда прошла, а проверка нет — код 1, `reason: "expect-failed"`, список расхождений — в
`items[].expectFailed`. Элемент `items[]`: `id`, `command`, `status` (`ok` | `failed` | `skipped` | `cancelled`),
`ok`, `exitCode`, `error`, `reason`, `data`, `output` (до 4000 символов), `expectFailed`, `seconds`. Общий
`output` итога — выводы шагов подряд, перед каждым строка `▸ <id> <команда> — ok|ошибка`.

**Остановка.** Ошибка шага со `stop` — остальные шаги `skipped`, кроме `always`. Отмена или срок вызова —
`cancelled`, кроме `always`. Шаг `always` после остановки не прерывается отменой вызова; его предел — свой
`timeout`, иначе 60 с. Код пакета — код первой ошибки (отмена — 7); пакет без ошибок — 0.

```json
{ "v": 1, "id": "…", "onError": "stop", "batch": [
  { "id": "build", "command": "build" },
  { "id": "run",   "command": "start", "args": ["--clear-logs"] },
  { "id": "check", "command": "logs", "args": ["--errors", "--since", "${run.logSince}"],
    "expect": { "data": { "rows": 0 } } },
  { "id": "stop",  "command": "stop", "always": true } ] }
```

Клиент **обязан** отказаться отправлять шаги серверу без `steps` в паспорте: тот проигнорировал бы `expect` и
вернул бы «успех».

#### 5.2.2. Блокировка

Сервер, объявивший `lock`, понимает `"lock": true` у запроса (одиночного или пакета): пока вызов идёт, чужие
вызовы, меняющие состояние, получают код 6, `reason: "busy"`, `data.busyWith` — id держателя. Проходят: команды,
объявленные `readOnly`, `trash.clean` и вызовы с `force`. Блокировка снимается вместе с итогом держателя. Что
считать меняющим, решает сервер по `readOnly` своих команд.

### 5.3. Принят — `active/<id>.json`

```json
{ "v": 1, "id": "…", "state": "running", "command": "test", "phase": "компиляция", "progress": 0.4,
  "accepted": "2026-01-15T09:03:01Z", "updated": "2026-01-15T09:03:09Z" }
```

- Сервер забирает запрос rename'ом из `requests/` в `active/` — это и есть «принят». Появление файла в `active/`
  значит: вызов будет доведён до итога, клиент может уходить.
- `state`: `running` или `waiting` — ждёт человека; тогда `asks` — что нужно:
  `{ "who": "human", "text": "Подтвердите выпуск на сервере сборки" }`.
- Сервер переписывает файл при смене фазы или прогресса.
- Сервер **может** дописывать вывод по ходу работы в `active/<id>.log` (обычный текст, только дописывание);
  клиент читает его хвост.

### 5.4. Итог — `done/<id>.json`

```json
{
  "v": 1, "id": "…", "state": "done",
  "ok": false, "exitCode": 1,
  "error": "2 теста не прошли", "reason": "tests-failed",
  "output": "parser::empty_input … FAIL\nparser::unicode … FAIL\n",
  "data": { "passed": 41, "failed": 2 },
  "artifacts": [ { "root": "project", "path": "reports/tests.xml", "kind": "application/xml" } ],
  "truncated": false,
  "accepted": "2026-01-15T09:03:01Z", "finished": "2026-01-15T09:03:44Z", "seconds": 43.2,
  "expires": "2026-01-15T09:08:44Z"
}
```

- Сервер **обязан** сначала записать итог, потом удалить `active/<id>.json`. Не записалось — повторять, `active/`
  остаётся.
- `error` — текст для человека. `reason` — стабильная машинная причина (из `channel.json` → `reasons`); клиенты
  ветвятся по `reason`, не по тексту.
- Для пакета — `items[]` по каждому элементу (поля — в 5.2.1).
- Прочитав итог, клиент переносит его в корзину (раздел 7). Не перенёс — итог лежит до `expires`, его можно
  прочитать ещё раз.

### 5.5. Жизненный цикл

```
requests/<id> ──(сервер: rename)──▶ active/<id> ──▶ done/<id> ──(клиент: rename)──▶ trash/ ──▶ удаляет сервер
   │   │                               ▲                └──(не забран, истёк expires)──▶ удаляет сервер
   │   └── просрочен / отменён ────────┘ итог с кодом 5 / 7
   └──(клиент: rename, отзыв)──▶ trash/
```

## 6. Сроки, отзыв, отмена

- **Просрочка.** Забирая запрос, сервер сравнивает его возраст (mtime по своим часам) с `timeout` + 60 с. Старше —
  не выполнять, итог с кодом 5 и `reason: "expired"`. Брошенный запрос не выполняется задним числом.
- **Срок выполнения.** `timeout` ограничивает и выполнение: к сроку сервер просит вызов отмениться (как при
  `cancel`), а если тот не закончился ещё через 30 с — закрывает его итогом с кодом 5 и `reason: "timeout"`;
  поздний итог отбрасывается. Выполнение, которое сервер умеет прервать сам (внешняя программа), прерывается к
  сроку с кодом 5.
- **Отзыв.** Клиент, уходя до принятия (прерван, вышел его срок), **обязан** перенести свой запрос
  `requests/<id>.json` → `trash/req-<id>.json`. Сервер забирает запрос таким же rename'ом, поэтому гонки нет:
  перенос удался — запрос отозван наверняка; файла уже нет — сервер его принял, итог будет.
- **Долгие вызовы при коротком сроке клиента.** У агентов вызов инструмента часто ограничен (минуты). Для долгих
  команд путь такой: `call --no-wait` (вернуть id, как только запрос в `active/`) → `wait <id> --max <с>` сколько
  угодно раз. `wait` без итога — код 5 с тем же id; вызов не теряется.
- **Отмена.** Клиент кладёт `cancel/<id>.json` (`{ "v": 1, "id": "…", "reason": "…" }`). Сервер: запрос ещё в
  `requests/` — убрать, итог с кодом 7; в `active/` — попытаться прервать, итог с кодом 7 (или обычный, если
  работа успела закончиться). Неотменяемая команда — обычный итог с `"cancelIgnored": true`. Файл отмены сервер
  удаляет. Отмена id, который уже выполнен, итог не трогает. Прерывая внешнюю программу, сервер **обязан**
  останавливать и её дочерние процессы (группа процессов, job object).

## 7. Корзина и уборка

- **Что попадает в корзину.** Прочитанный итог (`trash/done-<id>.json`), отозванный запрос (`trash/req-<id>.json`),
  брошенные клиентом временные файлы. Префиксы не дают одноимённым файлам затереть друг друга.
- **Порядок у клиента.** Удалить; нет права — перенести в `trash/`. Агенту **следует** один раз попросить у
  человека право удалять в папке канала, если его среда это позволяет; отказал — работать через корзину.
- **Команда `trash.clean [--dry]`** — стандартная, сервер **обязан** её поддерживать. Удаляет только обычные файлы
  прямо в `trash/` (без подпапок и ссылок). Выполняется самим сервером, без подопечного, и проходит любые
  блокировки. Итог — одна строка («Корзина: удалено 12 файлов, 48 КБ»), `data: { "files", "bytes" }`.
  Клиенту и агенту разрешено вызывать её без подтверждения человека.
- **Клиент чистит сам.** Если в корзине больше 50 файлов, клиент **следует** отправить `trash.clean` в фоне
  (`keep` = `minKeep`, итог не ждать).
- **Автоочистка.** Сервер раз в сутки удаляет из `trash/` файлы старше `limits.trashMaxAge` (по умолчанию 24 ч).
- **Уборка сервера** (раз в 10 с): итоги с прошедшим `expires`; итоги без `expires` старше часа; файлы `active/`
  без живого вызова старше часа; `*.tmp*` старше 10 минут; `cancel/` без вызова.

## 8. Пульс и восстановление

`alive.json` — сервер переписывает каждые `beat` секунд:

```json
{ "v": 1, "seq": 812, "at": "2026-01-15T09:05:00Z", "beat": 2,
  "server": "build-server", "version": "1.4.0", "pid": 4120,
  "state": "ready", "detail": { "worker": "idle" } }
```

- `state`: `ready`; `busy` — принимает, выполнит позже; `degraded` — принимает, часть возможностей недоступна
  (подробности в `detail`); `stopping`. Состояние подопечного — в `detail`.
- Клиент считает сервер неживым, если `seq` не менялся дольше `max(5 × beat, 10 с)` по своим часам; время
  изменения файла и поле `at` для этого не годятся. Запрос клиент кладёт сразу; если пульс стоит, а запрос так и
  не принят, — отзывает его и выходит с кодом 13. Принятый вызов — ждать до 90 с тишины, затем код 5: вызов не
  потерян. Чужой запрос (`wait` по id, который клиент не отправлял) не отзывается.
- **Перезапуск.** При старте сервер **обязан** закрыть всё, что лежит в `active/`: это вызовы прошлого экземпляра.
  Итог с кодом 4 и `reason: "server-restarted"`, если команда не объявлена `idempotent` (тогда **может**
  выполнить заново).
- **Остановка.** `state: "stopping"`, попросить текущие вызовы отмениться и дождаться их (или закрыть), удалить
  `alive.json`. Остановка по Ctrl+C / SIGTERM — тоже штатная.
- Нет ни `alive.json`, ни `channel.json` — сервера нет (код 10).
- Диагностика подопечного — в `state/`; клиент показывает её, когда ожидание затягивается.

## 9. Пути и крупные данные

- Путь в запросах и итогах — `{ "root": "<имя из roots>", "path": "относительный/путь" }`. Строкой — относительно
  корня `project` (или `channel`, если `project` нет). Абсолютный путь сервера **может** идти подсказкой `"abs"`;
  клиент на него не опирается.
- Крупное (отчёты, снимки, выгрузки) — файлами в `artifacts/` или под объявленным корнем; в итоге — ссылка.
  Срок хранения — `limits.artifactKeep`.
- Входные файлы клиент кладёт туда, куда разрешают `roots`, и передаёт ссылку.
- Сервер **обязан** проверять все пути: никаких `..`, абсолютных путей и выхода за объявленные корни.

## 10. inbox и state

- `state/*.json` — снимки (состояние сервера, списки, индексы). У каждого — поле `updated`. Только чтение.
- `inbox/<key>.json` — **уровень, а не очередь**: файл лежит, пока ситуация требует действия клиента, и исчезает,
  когда она разрешилась.

```json
{ "v": 1, "key": "r-17", "why": "задача сдана: принять или вернуть", "since": "2026-01-15T08:40:00Z",
  "suggest": [ { "command": "record.status", "params": { "record": "r-17", "to": "done" } } ],
  "ref": { "root": "channel", "path": "state/records/r-17.json" } }
```

`suggest` — готовые запросы, которые клиент кладёт в `requests/` почти без правок.

- Сервер **может** вести счётчик `inbox/.seq` (и `state/.seq`) — число, растущее при каждом изменении. Клиент ждёт
  событий, следя за счётчиком (`watch`), а не перечитывая всё.

## 11. Поиск канала

Клиент в песочнице видит только примонтированные папки, а не реестры и настройки сервера. Порядок поиска:

1. явно: `--channel <путь>` или переменная `EFC_CHANNEL`;
2. `channel.json` вверх от текущей папки (в ней самой и в подпапках `.efc/`);
3. указатель `.efc-channels.json` в корне примонтированной папки — его пишет сервер, открывая канал:

```json
[ { "name": "app-build", "path": "build/.efc", "title": "Сборка приложения" } ]
```

`efc list` показывает найденные каналы с состоянием пульса.

## 12. Безопасность

- Кто может писать в папку канала, тот может просить. Канал создаётся только там, где его явно включили, и
  удаляется при выключении.
- Папку канала **обязательно** исключать из синхронизации (облака, git — `.gitignore` со `*`, средства
  репликации): иначе запросы приедут на другую машину. Вторая линия защиты — `instance` (раздел 4).
- `from` — подпись, а не пропуск. Права определяет сервер. Опасное (управление машиной, запуск произвольных
  программ, удаление данных) — только через подтверждение человека (`state: "waiting"`, `asks`); отказ — код 8.
- Токены и секреты в канал не пишутся.
- Клиент, которого сервер кладёт в канал (`efc`), **следует** сопровождать контрольной суммой в `channel.json`
  (`client: { "file": "efc", "sha256": "…" }`).

## 13. Коды выхода

`exitCode` в итоге; они же — код процесса клиента.

| Код | Смысл |
|---|---|
| 0 | успех |
| 1 | ошибка выполнения |
| 2 | неверный запрос или аргументы |
| 3 | нет такой команды |
| 4 | исключение или прервано (в т. ч. перезапуск сервера) |
| 5 | срок вышел (запрос просрочен или клиент не дождался — итог позже по id) |
| 6 | занято (идёт другой меняющий вызов; `data.busyWith` — его id) |
| 7 | отменено |
| 8 | отказано (нет прав, человек не подтвердил) |
| 10 | нет сервера |
| 11 | цель не однозначна (несколько каналов подходят) |
| 12 | подопечный не отвечает, запрос не отправлен |
| 13 | сервер не отвечает (пульс стоит) |

Стандартные `reason`: `expired`, `cancelled`, `server-restarted`, `busy`, `no-approval`, `bad-request`,
`unknown-command`, `foreign-instance`, `too-large`, `timeout`; для шагов пакета — `bad-reference`, `expect-failed`,
`step-timeout`.

## 14. Стандартные команды

| Команда | Обязательна | Что делает |
|---|---|---|
| `help [команда]` | следует | список команд или описание одной |
| `trash.clean [--dry]` | да | очистить корзину (раздел 7) |
| `ping` | следует | ответ `pong` — проверка пути «запрос → итог»; на ней держится `efc check` |

## 15. Версии и совместимость

- `protocol` в `channel.json` — `efc/<старшая версия>`. Клиент **обязан** отказаться работать с незнакомой
  старшей версией и сказать это прямо.
- Внутри старшей версии — только добавления: новые поля необязательны, неизвестные поля пропускаются, смысл
  существующих не меняется.
- Поле `v` в каждом файле — старшая версия формата этого файла.

## 16. Соответствие

**Сервер обязан:**

1. При старте: раскладка (с `trash/`), `.gitignore`, `channel.json` (`instance`, `howToStart`), `README.txt`,
   запись в `.efc-channels.json`; закрыть хвосты `active/`. Чужой `instance` — не обслуживать.
2. Пульс каждые `beat` секунд, `seq` растёт.
3. Опрашивать `requests/` не реже чем раз в 200 мс; брать только `*.json` с допустимым id, по возрастанию id.
4. Забирать rename'ом в `active/`; не вышло — пропустить (забрал другой или файл занят).
5. Проверять размер, JSON, `command`, просрочку — иначе итог 2 / 3 / 5.
6. Писать фазы в `active/`; ожидание человека — `state: "waiting"` + `asks`.
7. Итог — атомарно, затем удалить `active/`; не записалось — повторять.
8. Отмена (с дочерними процессами), срок выполнения, `trash.clean` (в обход очереди), автоочистка корзины,
   уборка по разделу 7.
11. Периодически проверять паспорт: чужой `instance` — не обслуживать, пропавший — записать заново.
12. Файлы канала — только новым файлом и rename, никогда на месте.
9. Пути — только внутри `roots`; секреты не писать.
10. Ничего не требовать от клиента, кроме записи файлов и rename.

**Клиент обязан:**

1. Писать атомарно; id — по разделу 3.5.
2. Никогда не полагаться на удаление: при отказе — `trash/`.
3. Отзывать непринятые запросы переносом; принятые — ждать или оставлять с id.
4. Судить о живости по `seq` и своим часам.
5. Печатать `howToStart` при кодах 10 и 13.
6. Отказываться от незнакомой старшей версии протокола.
