# EFC — файловый канал

Стандарт и инструменты для обмена вызовами между программой и её клиентом через общую папку — когда прямой
связи нет: клиент (агент, скрипт) работает в виртуальной машине, контейнере или песочнице и видит только
примонтированную папку.

```
клиент                         канал (общая папка)                          сервер
  │  requests/<id>.json  ──▶   requests/ → active/ → done/   ◀── забирает, выполняет, пишет итог
  │  ◀── читает итог           alive.json (пульс), channel.json (паспорт)
  └─ прочитанное → trash/      trash/ ──▶ чистит сервер
```

Протокол: `efc/1`. Текст стандарта — [SPEC.md](SPEC.md).

## Чем это лучше, чем «просто положить файл»

- Запись атомарная: итог не читается наполовину.
- Видно, что вызов принят (`active/`), на какой он фазе и не ждёт ли человека.
- Брошенный запрос не выполняется задним числом; непринятый запрос отзывается без гонки.
- Пульс сервера и восстановление после его перезапуска.
- Клиенту не нужно право удалять файлы: всё, что он убирает, он переносит в корзину, а чистит сервер.
- Канал описывает себя сам: `channel.json` перечисляет команды, лимиты и подсказывает человеку, как запустить сервер.
- Быстро: вызов укладывается примерно в 20 мс плюс задержку самой общей папки.

## Состав

| Путь | Что |
|---|---|
| `SPEC.md` | стандарт `efc/1` |
| `schemas/` | JSON Schema всех файлов канала |
| `examples/` | примеры файлов канала, проверенные схемами |
| `crates/efc-core` | библиотека на Rust: протокол, клиент, сервер, проверочный набор |
| `crates/efc` | один исполняемый файл `efc`: клиент, `serve`, `check`, `init` |
| `build.cmd`, `build.sh` | сборка под Windows и статическая сборка под Linux |
| `skill/SKILL.md` | навык для агента: как вызывать через канал |

## Сборка

```
build.cmd                 Windows → dist\efc.exe
./build.sh                Linux   → dist/efc-x86_64-unknown-linux-gnu (статический, без зависимостей)
cargo test                все проверки: протокол, живой сервер, сквозные прогоны бинарника (Windows, Linux, macOS)
```

Нужен Rust 1.75+. Зависимости — только `serde`, `serde_json`, `sha2`.

## Клиент

```
efc list                                   каналы рядом: вверх от текущей папки, .efc-channels.json, EFC_PATH
efc [--channel <папка|имя>] help           команды сервера
efc call build --release                   вызвать и дождаться итога (всё после имени команды — её аргументы)
efc --params '{"record":"r-17"}' call record.show
efc batch steps.json                       пакет команд одним вызовом
efc --no-wait call test                    напечатать id, как только вызов принят (код 0)
efc --max 170 wait <id>                    ждать итога не дольше 170 с; не дождался — код 5, вызов идёт дальше
efc result <id>                            итог, если уже есть
efc cancel <id>                            попросить отменить
efc diag                                   пульс, очередь, кто ждёт человека, корзина, что делать
efc trash [--clean] [--dry]                корзина канала
```

Флаги: `--json` (итог JSON-ом), `--timeout <с>` (срок запроса), `--keep <с>` (сколько хранить итог), `--max <с>`
(сколько ждать клиенту), `--force`, `--from <имя>`.

Окружение: `EFC_CHANNEL` (канал по умолчанию), `EFC_PATH` (где ещё искать каналы, через `:` или `;`),
`EFC_FROM` (подпись запросов), `EFC_NO_DELETE=1` (не пытаться удалять — сразу в корзину).

Код выхода — код вызова: 0 успех, 1 ошибка, 2 аргументы, 3 нет команды, 4 сбой, 5 срок, 6 занято, 7 отменено,
8 отказано, 10 нет сервера, 11 канал не однозначен, 13 сервер не отвечает. При кодах 10 и 13 клиент печатает
подсказку из паспорта — что запустить человеку.

### Пакеты и шаги

Несколько команд одним вызовом — `efc batch файл.json` (или `-` из stdin):

```json
{ "onError": "stop", "batch": [
  { "id": "build", "command": "build" },
  { "id": "run",   "command": "start", "args": ["--clear-logs"] },
  { "id": "check", "command": "logs", "args": ["--errors", "--since", "${run.logSince}"],
    "expect": { "data": { "rows": 0 } } },
  { "id": "stop",  "command": "stop", "always": true } ] }
```

- `${шаг.путь}` — значение из `data` уже выполненного шага (а также `exitCode`, `output`, `ok`);
- `expect` — проверка: `exit` (ожидаемый код), `output` / `notOutput` (подстрока), `data` (поля);
- `always` — выполнить и после ошибки или отмены; `onError` и `timeout` — у отдельного шага;
- `--lock` — пока идёт пакет, чужие меняющие вызовы получают код 6 (`--force` проходит).

Итог — `items[]` по каждому шагу (`status`: `ok`, `failed`, `skipped`, `cancelled`). Шаги и `lock` сервер
объявляет в паспорте (`steps`, `lock`); серверу без них `efc` такой пакет не отправит.

### Долгие команды при коротком сроке вызова

У агентов вызов инструмента обычно ограничен минутами. Долгое — так:

```
id=$(efc --no-wait call test)
efc --max 170 wait "$id"     # повторять, пока код 5
```

## Отладка первых запусков

Новая машина или ОС — сначала так:

```
efc selftest [папка]          # на машине сервера: файловая система + сервер и клиент в одном процессе
efc --trace --channel X serve …   # сервер с трассировкой
efc --trace --channel X call …    # клиент с трассировкой (или EFC_TRACE=1 в окружении)
efc --channel X trace --last 60   # журнал обеих сторон по времени; --id <id> — один вызов, --raw — как есть
efc --channel X bench -n 20       # задержки: сколько запрос ждал сервер, сколько работа, сколько доставка
efc --channel X diag              # пульс, очередь, кто ждёт человека, корзина, что делать
```

- `selftest` проверяет то, что на Windows чаще всего ведёт себя иначе: rename поверх файла, который держит другая
  программа без разрешения на замену (антивирус, редактор, индексатор), — какой код ошибки даёт ОС и дожидается ли
  его повтор; удаление такого файла; кириллицу и пробелы в путях; пути длиннее 260 символов; регистр имён;
  точность времени изменения файлов и расхождение часов файловой системы; разрешено ли удаление. Затем поднимает
  сервер и клиент в одном процессе на этой же файловой системе и прогоняет проверочный набор (с правом удалять и
  без него) и 20 вызовов `ping`. Свою временную папку убирает.
- Трассировка пишется в `<канал>/trace/server-<дата>.jsonl` и `client-<дата>.jsonl` — по строке JSON на событие:
  забрал запрос (и сколько он пролежал), принял, фаза, итог (и сколько писался), не смог удалить, повторял rename
  (с кодами ошибок ОС 5/32/33), пульс опоздал, отмена, срок. Журнал лежит в канале, поэтому клиент в ВМ видит и
  то, что происходило у сервера на хосте. Файлы старше 3 суток сервер удаляет сам.
- `EFC_TRACE=stderr` — в поток ошибок, `EFC_TRACE=<файл>` — в свой файл.

## Сделать каналом любую консольную программу — `efc serve`

```
efc --channel ./.efc serve --allow "build=cargo,test=cargo" --cwd . --index .. --title "Сборка"
```

- `--allow имя[=программа],…` — белый список; программа запускается напрямую, без оболочки, аргументы клиента
  идут ей как есть.
- `--confirm имя,…` (или `*`) — каждый вызов подтверждает человек в терминале сервера; без терминала — отказ (код 8).
- `--config файл.json` — то же из файла, с постоянными аргументами, запретом своих аргументов и пределом времени:

```json
{
  "title": "Сборка",
  "howToStart": "Запустите на сервере сборки: efc --channel D:/app/.efc serve --config D:/app/efc-serve.json",
  "commands": [
    { "name": "build", "program": "cargo", "args": ["build", "--release"], "fixed": true, "summary": "Собрать" },
    { "name": "test",  "program": "cargo", "args": ["test"], "timeout": 900, "summary": "Тесты" },
    { "name": "deploy", "program": "deploy.cmd", "fixed": true, "confirm": true, "summary": "Выложить" }
  ]
}
```

- `--cwd` — рабочая папка программ (и корень `project` для путей в ответах), `--index <папка>` — вести там
  указатель `.efc-channels.json`, `--client <файл>` — положить в канал клиент (с контрольной суммой в паспорте),
  `--take-over` — забрать канал с чужим `instance`.

Осторожно: программа из белого списка получает любые аргументы клиента. Для команд, которым это опасно,
используйте `fixed` и `confirm`.

## Встроить сервер в свою программу (Rust)

```rust
use efc_core::server::{Ctx, Handler, Outcome, Server, ServerConfig};
use efc_core::model::{CommandInfo, Op};
use std::sync::Arc;

struct App;

impl Handler for App {
    fn commands(&self) -> Vec<CommandInfo> {
        vec![CommandInfo::new("build", "Собрать проект", "build [--release]").long()]
    }

    fn run(&self, ctx: &Ctx, op: &Op) -> Outcome {
        ctx.set_phase("компиляция", Some(0.3));
        if ctx.cancelled() {
            return Outcome::cancelled();
        }
        Outcome::ok("собрано\n")
    }
}

fn main() {
    let mut cfg = ServerConfig::new("./.efc", "my-app", "1.0.0");
    cfg.how_to_start = "Запустите my-app".into();
    let _server = Server::start(cfg, Arc::new(App)).expect("канал");
    // … программа работает; `server.stop(…)` — штатная остановка
}
```

Сервер берёт на себя весь протокол: паспорт, пульс, приём и просрочку запросов, пакеты с шагами и блокировкой, отмену, ожидание
человека (`ctx.ask_human`), итоги с повтором записи, восстановление после перезапуска, уборку, корзину
(`trash.clean` и раз в сутки) и встроенные `help`, `ping`. Для других языков — по SPEC и схемам; проверить
свою реализацию — `efc check --channel <папка>`.

## Для авторов серверов

- `efc init <папка> [--server имя] [--title …] [--how-to-start …]` — заготовка канала.
- `efc check` — проверочный набор против живого сервера (14 проверок: паспорт, пульс, итог, неизвестная
  команда, битый JSON, несовпадение id, просрочка, чужие файлы, повтор id, отзыв, пакет, шаги пакета, корзина,
  help). Пакет и шаги проверяются, если сервер их объявил.
  Вызывает только стандартные и заведомо несуществующие команды — безопасно для рабочего сервера.
